# Boards and blocking in the public API

Status: **deployed on 21 September 2026 (Europe/Stockholm)** after the user's explicit “Yes deploy” approval. No APK or GitHub release was published or replaced. Future deployments still require approval under [release-approval.md](release-approval.md).

## Scope

The existing OAuth API now exposes the regular Boards features: browsing and private membership, notes/replies/drawings, Yeah reactions, spoilers, immutable draft revisions, activity and preferences, invitations/codes, proposals, owner controls, local moderation and appeals, artwork imports and stationery purchases. Blocking and Block Messages have separate read/write scopes.

Central staff tools remain dashboard-only. `private.has_permission` refuses OAuth identities, so a connected app cannot inherit its account's dashboard permissions. Native staff sessions retain their existing access. The API has no direct creation/approval, global suspension, central private-review, permanent deletion, word-filter, catalogue-editing or feature-setting endpoints.

Existing apps gain no scopes automatically. The portal and consent screen already use the server's scope catalogue; developers must request the new scopes and users must consent again. Local board roles are enforced in addition to OAuth scopes. Cloud drafts have a separate owner-private scope, and stationery spending requires explicit purchase permission.

## Files and boundaries

- `infra/supabase/public-api/boards.json` is the endpoint/field/scope contract. Tests compare it with the SQL allowlist. Native Boards operations remain inaccessible directly to `api_client`.
- `20260921000100_public_api_boards.sql` adds scopes, the scoped adapter, strict input validation, bounded pages and role checks. It reuses the native Boards mutation functions and access rules.
- `20260921000200_public_api_blocking.sql` adds `blocks.list`, `blocks.set`, `privacy.get`, `privacy.set`, typed privacy errors and scoped realtime invalidations. The native block mutation and message/group privacy triggers enforce the same behavior for both kinds of client.
- `20260921000300_public_api_board_media.sql` retains an upload's OAuth client identity, checks its consent/scope again at commit, and prevents replaying another action's result as a completed upload.
- `board-media/server.py` handles `/v1/boards.artwork_upload` using the existing image sanitizer. Only the service role can commit processed pixels. The native `/boards/media` route remains supported.
- `developer/docs.html` documents all endpoints, scopes, payloads, media limits and realtime topics. Its Boards endpoint table is generated by `public-api/update-docs.mjs`.

Private realtime events contain `{}` only; clients must refetch through the authenticated API. Board drafts, blocks and privacy preferences each have their own scope/topic. The legacy `notifications:` topic no longer includes private board IDs in Boards invalidations. As with the existing Realtime service, an already-authorized subscription can remain open until token refresh/expiry, but its events carry no protected content.

Board artwork is checked before pixel decoding and again before commit. Access loss, consent revocation, app suspension or scope removal prevents a pending upload from publishing. Ordinary board notes still accept validated strokes only, not imported images, GIFs or audio.

## Local validation

Run from the repository root, with Node and Python available:

```powershell
$env:BOARDS_TEST_PUBLIC_API = '1'
node --test infra/supabase/tests/boards/api.test.mjs infra/supabase/tests/boards/database.test.mjs
node infra/supabase/public-api/update-docs.mjs --check
python -m unittest discover -s infra/supabase/board-media -p test_server.py -v
```

The Python suite requires Pillow. PGlite is provided by `infra/supabase/push/node_modules` (`npm ci` in that directory installs the declared dependencies).

Verified locally: 57 database tests and 12 media-service tests pass. The database run includes all 37 existing native Boards regression tests **after applying the new API migrations**, plus 20 OAuth API tests. Coverage includes scoped grants and revocation, private reads/media, local hierarchy and central exclusion, membership/codes, archive/transfer, drafts/conflicts, filtering, reports/appeals, purchases, idempotency, blocking, DM/group privacy, realtime, rate limits and the emergency switch.

PGlite uses a minimal Supabase service fixture and deterministic test-only crypto substitutes. HTTP media tests use a local server and mocked RPC transport while testing real image processing. Production verification is recorded below.

## Future deployment procedure (requires fresh approval)

1. Apply the three new migrations in order through the existing migration runner. All existing Boards migrations, through `20260919000800`, must already be applied. Do not edit applied migration files or change the current feature switch.
2. Rebuild/restart `board-media` and validate/reload Caddy for the additional upload route. Deploy the updated developer documentation. Existing native endpoints and release versions stay unchanged.
3. With an explicitly authorized test account/application, verify HTTP scope denials, consent expansion/revocation, public/private reads, blocked invites, idempotent mutations, an artwork upload, and private realtime subscriptions. Verify that an OAuth token belonging to dashboard staff cannot use central privileges.
4. Confirm existing app Boards and message privacy still work. Do not publish or replace an APK as part of this backend/API deployment.

For an emergency, suspend the affected developer app or remove its new scopes using existing dashboard controls. The Boards feature switch still stops board API reads/mutations while preserving data and leaving `boards.settings` available. Blocking/privacy controls remain available independently. Schema rollback is not required to disable access.
