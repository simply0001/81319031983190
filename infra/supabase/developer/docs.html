Build with PocketPass

Connect PocketPass accounts to your app. With each person's permission, you can use their profile, friends, messages, Boards, activity, blocking settings and game progress.

PocketPass is a friend-finding and messaging app for handheld consoles and phones. The public API is a curated JSON API behind standard OAuth 2.1: register an app in the developer portal, send users through the consent flow, and call POST https://api.pocketpass.xyz/v1/<resource>.<action> with the token you get back.

The flow in one paragraph: your app sends the user to the authorization endpoint with a PKCE challenge. PocketPass signs the user in (email code, Discord, or a username and password) and shows a consent screen listing your app and the permissions you registered. On approval the user is redirected back to you with a one-time code, which you exchange for an access token (valid one hour) and a refresh token. From then on you call the API with Authorization: Bearer <access token>.

A few things that make this API different from a generic backend:

  • Permissions are app-level. You choose the PocketPass scopes when you register the app; every user of your app grants the same set. The OAuth scope= parameter only covers OpenID claims (see Scopes).
  • Every request is a POST with a JSON object body, even reads, and every response is a JSON object. Errors are JSON objects too, with a stable code and hint.
  • The token only works on the public API. A connected app cannot reach the first-party endpoints PocketPass itself uses. Available actions are listed in the endpoint reference, Boards and blocking and privacy, plus media and Realtime with the same token and the matching scopes.
  • Users can disconnect you at any time and PocketPass can suspend an app. Your code needs to handle a token that suddenly stops working (see Tokens).

Getting started

Kotlin & JavaScript examples →

1. Create a PocketPass account

The portal signs you in with a normal PocketPass account — there is no separate developer login. If you do not have one yet, download PocketPass, create the account in the app (email code or Discord), then sign in at developer.pocketpass.xyz with the same email or Discord account.

2. Register an app

Every account can register up to five apps. An app has:

  • Name, description, website and logo URL — shown on the consent screen so users know who is asking. Names cannot contain "PocketPass". Website and logo must be https:// URLs.
  • Redirect URIs — where users are sent back after consent. Exact-match only; see Redirect URIs.
  • Client type — public or confidential (below). Fixed at registration.
  • Permissions — the PocketPass scopes your app needs. Pick the smallest set that works; adding a scope later disconnects your existing users (see Changing scopes).

Registration gives you a client id (a UUID) and, for confidential clients, a client secret that is shown exactly once. Copy it straight into your server's secret store. If you lose it, rotate it from the app page; the old secret stops working the moment you do.

3. Choose the right client type

TypeUse it forToken endpoint authentication
Public Websites and single-page apps, browser extensions, desktop and mobile apps, CLI tools — anything that ships to the user's device and therefore cannot keep a secret. None. PKCE protects the code exchange. Send client_id in the request body.
Confidential Server-side apps where the token exchange happens on a machine you control (a web backend, a bot, a worker). HTTP Basic with client_id as the username and the client secret as the password, on every token request. PKCE is still required.

When in doubt pick public: a confidential client that leaks its secret is worse than a public one that never had it. PKCE is mandatory for both.

4. Test it

The app page in the portal has a Test connect button. It generates a PKCE verifier and state in your browser, opens the consent flow for your first redirect URI in a new tab, and shows you the exact curl commands to exchange the code and call session.get. Use it before writing any code so you know what the redirect looks like.

Connecting a user

Kotlin & JavaScript examples →

The connect flow is a standard OAuth 2.1 authorization code flow with PKCE (S256). Requests without a PKCE challenge are refused at the gateway.

Step 1 — generate a verifier, a challenge and a state

Create 32 random bytes and base64url-encode them: that is your code_verifier. Hash it with SHA-256 and base64url-encode the digest: that is your code_challenge. Generate a second random string as state. Keep both the verifier and the state somewhere tied to this user's session (a cookie, sessionStorage, a row in your database) — you need them when the user comes back.

Step 2 — send the user to the authorization endpoint

The URL is https://api.pocketpass.xyz/auth/v1/oauth/authorize with client_id, a registered redirect_uri, response_type=code, scope, code_challenge, code_challenge_method=S256 and state.

Open this URL in the user's browser (a full navigation on the web, the system browser or a custom tab on mobile and desktop — never a web view you control). PocketPass redirects to the consent screen at https://links.pocketpass.xyz/oauth/consent, where the user signs in if needed and sees your app's name, website, description and the PocketPass permissions you registered. If the user already has a live grant for your app the screen is skipped and they land straight back on your redirect URI.

Step 3 — handle the redirect

On approval the browser lands on your redirect_uri with ?code=…&state=…. On denial it lands there with ?error=access_denied&state=…. Always check that state matches the value you stored before doing anything with the code.

Step 4 — exchange the code for tokens

Codes are single-use and expire ten minutes after they were issued. Send it to POST https://api.pocketpass.xyz/auth/v1/oauth/token as application/x-www-form-urlencoded (JSON with Content-Type: application/json is accepted too), with grant_type=authorization_code, the code, the same redirect_uri, the code_verifier and, for public clients, your client_id.

Confidential clients leave client_id out of the body and send Authorization: Basic base64(client_id:client_secret) instead. The response has access_token, token_type (bearer), expires_in (3600 seconds), refresh_token and id_token.

Store the access token and the refresh token per user. You can ignore id_token; the user id it carries is also returned by session.get and me.get, which is the reliable way to know who just connected.

Step 5 — check the connection

session.get needs no scope and returns the user id, your client id, the scopes the user granted and your remaining rate-limit budget. It is the right first call after every connect and a good health check afterwards.

Websites (public clients)

The API sends CORS headers, so a browser app can call /v1/… directly with the access token. Remember that anything in the browser is visible to the user, which is why a website is a public client.

Native apps (public clients)

Desktop and CLI apps listen on a loopback port and register http://127.0.0.1:<port>/callback as the redirect URI.

Mobile apps do the same with a custom scheme (com.example.app:/callback) or an https App Link / Universal Link, opened in the system browser or an in-app browser tab.

Servers (confidential clients)

The browser part is the same. Run the code exchange on your server, with the client secret from your secret store.

Redirect URIs

Kotlin & JavaScript examples →

The redirect_uri in the authorization request and in the token exchange must match one of the URIs registered for your app exactly — same scheme, host, port, path, and no extra query or fragment. Wildcards and prefix matching are not supported.

  • https URIs are allowed for any host.
  • Custom schemes (com.example.app:/callback) are allowed for native apps.
  • http is allowed only for localhost, 127.0.0.1 and [::1]. Because the match is exact, register the port you will actually listen on — http://127.0.0.1:8765/callback, not http://127.0.0.1/callback — and pin that port in your app. If you are unsure which name the platform will use, register both http://localhost:8765/callback and http://127.0.0.1:8765/callback.
  • Rejected: javascript:, data:, file:, blob:, about:, vbscript:; URIs with a fragment (#), a comma, whitespace or control characters; anything without a scheme and host.
  • At most 10 URIs per app, each at most 2048 characters.

You can add and remove redirect URIs at any time from the app page; the change is live immediately and does not disconnect anyone.

OpenID scopes (the scope= parameter)

The scope= parameter of the authorization request is OpenID Connect only. Send scope=openid. Add email, profile or phone only if you need those claims in an ID token or from /auth/v1/oauth/userinfo — each one is shown to the user as an extra thing you will see ("your email address", "your PocketPass username", "your phone number"). The consent screen refuses a request with any other scope, including PocketPass scopes. Email is not available through me.get or ordinary profile requests. For almost every app me.get gives you what you need without asking for OpenID claims.

Tokens

Kotlin & JavaScript examples →

Lifetimes

  • Access token: a JWT valid for one hour (expires_in: 3600). Send it as Authorization: Bearer …. Treat it as opaque; do not rely on its claims.
  • Refresh token: long-lived and rotating. Every refresh returns a new refresh token and invalidates the one you used. Always persist the newest pair before you use it; if two of your processes race to refresh the same token, the second one fails and you have to reconnect the user.
  • Authorization code: single-use, ten minutes.

Refreshing

Send grant_type=refresh_token and the refresh_token to the same token endpoint, with your client_id for a public client or HTTP Basic for a confidential one.

Refresh a little before expiry (for example when fewer than 60 seconds remain) or on the first 401, then retry the request once. A refresh that answers 400 with "error": "invalid_grant" means the grant is gone — the user disconnected your app, PocketPass suspended it, you changed the app's scopes, or the refresh token was already rotated. Drop the stored tokens and offer the user the connect flow again. invalid_client means your client id, secret or client type is wrong. While the user's account is banned, the token endpoint answers 403; see ACCOUNT_BANNED under Errors.

Revocation

Three things end a connection. API calls stop at the next request. A Realtime channel that is already open keeps receiving until its access token expires (at most one hour), and signed URLs work until they expire (at most 15 minutes).

  • The user disconnects you on https://links.pocketpass.xyz/oauth/apps. Existing access tokens answer PT401 CONSENT_REVOKED, refresh fails with invalid_grant.
  • Your app calls session.revoke (the "disconnect" button in your own UI). Same effect, scoped to that user. Discard the tokens afterwards; the call is idempotent, so retrying is safe.
  • PocketPass suspends the app. Every call answers PT403 APP_SUSPENDED and the token endpoint refuses the client.

Connected apps cannot use the account endpoints PocketPass itself uses: /auth/v1/logout, /auth/v1/user, multi-factor and grant-management endpoints all answer 403 for an app token. Disconnecting is POST /v1/session.revoke, nothing else.

Never put an access token in a URL, a log line or client-side analytics. If you suspect a token or secret leaked, rotate the secret in the portal (confidential clients) and have affected users disconnect and reconnect.

Calling the API

Kotlin & JavaScript examples →

Every endpoint is POST https://api.pocketpass.xyz/v1/<resource>.<action> with Authorization: Bearer <access token> and Content-Type: application/json headers and a JSON object body — {} when the endpoint takes no arguments.

Rules that hold everywhere:

  • Only POST (and OPTIONS for CORS preflight). A GET is a 404.
  • The body must be a JSON object; anything else, including invalid JSON, is PT400 INVALID_FIELD. Unknown keys are rejected with PT400 UNKNOWN_FIELD, so typos fail loudly instead of silently doing nothing.
  • Every response body is a JSON object. Successful responses are 200. Errors carry a 4xx/5xx status and a body { "code", "message", "hint" } — branch on hint, show message to a developer, never to an end user.
  • Lists return { "items": [...], "next_cursor": null | "…" }. Pass next_cursor back as cursor to get the next page; null means you have everything. Cursors are opaque strings — do not build or parse them.
  • limit is clamped to 1…100 and defaults to 50.
  • Single objects come wrapped in their resource name: { "profile": {…} }, { "conversation": {…} }, { "message": {…} }.
  • Timestamps are ISO 8601 with a timezone offset; ids are UUIDs.
  • An unknown path under /v1/, such as /v1/friends.nope, answers 404 with { "code": "PT404", "message": "Unknown endpoint", "hint": "UNKNOWN_ENDPOINT" }.

Boards

Kotlin & JavaScript examples →

Boards use the same bearer token and POST /v1/… convention as messages. Register the scopes your app needs and obtain fresh consent before using them. Existing connected apps do not gain Boards or blocking access automatically.

Public boards are readable by signed-in users; private boards require membership. Joining is required to publish, reply or react. OAuth scopes never replace these rules: owner actions require ownership, moderator actions require a local board role, and blocks, restrictions, archiving and the Boards feature switch are enforced on the server.

Requests and pagination

All mutations below require operation_id, a UUID generated once per user action and reused with the identical payload on retries. Other IDs are UUIDs except stationery_id, which is a catalogue string. Unknown fields are rejected. A field marked ? is optional; booleans must be JSON booleans. The JSON request limit is 600,000 bytes, except for artwork uploads.

Paginated reads accept limit (default 30, clamped to 1–100) and an opaque cursor. Pass the returned next_cursor unchanged with the same filters until it is null; a final empty page is possible. Cursors cannot be moved between endpoints or filters. Management and notices paginate each queue together. Reads always recheck current access, including when a cursor was issued before a membership or privacy change.

boards.list uses scope: "joined" by default; choose "explore" for the public directory, with an optional name search. Feed sort is "newest" (default), "activity" (new replies) or "popular" (Yeah count, then creation time). Popular period is "today", "week" (default) or "all". Replies are chronological.

Notes, replies and spoilers

A note has text, one drawing, or both. Text and captions are limited to 1,000 characters; replies to 500. Use thread_id to reply to a top-level note and optional reply_to to identify a particular note in that thread. Imported images, GIFs and audio cannot be attached to board notes.

Note objects include id, board_id, author_id, author_name, author_avatar, thread_id, reply_to, body, drawing, a versioned stationery snapshot, spoiler, has_drawing, removed, creation/activity/edit timestamps, yeah, yeah_count, reply_count and mentions (the people mentioned, as user_id and name). Avatar downloads retain the existing profile:read requirement.

Spoilers return an empty body and no drawing, stationery or preview until the user explicitly reveals them with boards.post or boards.preview and reveal: true. Activity previews contain no note text. Removed notes remain as placeholders so replies stay readable. Published drawings cannot be edited.

Drawing format

A drawing is { "version": 1, "width": 800, "height": 600, "strokes": [...] }. Each stroke has pen, color, size and points as [x, y] pairs.

The paper is always white and 4:3. Pens are pixel, smooth and eraser; sizes are numbers from 1 to 40. Colours are #222222, #E84A5F, #F6B93B, #4CAF70, #3379D6, #9564C8 and #FFFFFF. Each stroke needs at least one point inside the 800×600 canvas. Limits are 1,000 strokes, 20,000 total points and 524,288 bytes of validated drawing JSON. Unknown fields and external media are rejected. Render the strokes locally or use boards.preview for a static SVG generated by the server.

Draft recovery and publishing

boards.save_draft takes a persistent draft_id, a new revision_id, optional base_id for the revision being replaced, and a payload containing body, drawing, spoiler, stationery_id, thread_id, reply_to and/or branding_kind (icon or cover). Saving never publishes. Concurrent edits keep separate heads and return conflict: true; let the user choose what to keep.

Cloud drafts are private to their author, including when a board moderator or dashboard staff member reviews the board. Keep a local copy during failures. If BOARD_DRAFT_BASE_EXPIRED is returned, recover the attempted content as a new revision without a base rather than overwriting another device's head.

When the user chooses Publish, include draft_id, draft_revision_id and, when needed, draft_base_id along with the explicit content. This additionally requires boards:drafts. A successful publish retires only those matching revisions; other conflicts survive. A failure leaves the draft intact. Reuse the original operation ID and payload after an uncertain result.

Membership, moderation and notifications

Owners choose join_policy and code_policy as open or approval, plus members_can_invite. Direct invitations always require acceptance. Codes remain valid until revoked or their inviter loses access. Public boards can become private; private boards cannot become public. Archiving keeps the existing audience able to read while participation and invitations stop.

Board names allow 1–60 characters, descriptions 1,000 and rules 4,000. Accent values are blue, green, pink, purple, orange and teal. Staff word rules apply to new submissions and edits. A censoring rule replaces matches with ****; a blocking rule rejects the submission with its reason. Old content is not automatically rescanned.

Moderators can use review: true on supported reads to inspect blocked content for their own boards, requiring both boards:read and boards:moderate. Deleting or changing another author's spoiler flag requires both boards:write and boards:moderate, with a reason; use review: true when a block would otherwise hide it. Retained artwork also requires boards:moderate. Reviews and moderation actions are logged.

Restrictions use kind: "mute" or "ban", with optional ISO 8601 expires_at. Bans prevent participation and revoke private membership; public boards remain readable. Reports concerning an owner/moderator go to PocketPass staff. Report queues omit reporter identity. Resolutions use status: "resolved" (default) or "dismissed" and a reason. Removed content and previous versions follow the existing 30-day retention policy, extended for active cases.

boards.preferences controls per-board muted and push_enabled; boards.push_preference controls the separate global board push preference. New memberships receive in-app and push activity by default, excluding the person's own actions. Activity is grouped by thread. Each inbox item has a kind: mention, reply (to the person's note or reply), yeah, note, activity, or report for moderators. Connected apps use scoped Realtime events and boards.inbox; registering a third-party push device is not exposed.

Board artwork and stationery

For a drawn icon or cover, use boards.draw_branding. Imported branding uses POST /v1/boards.artwork_upload, with boards:manage and a JSON body of board_id, kind: "icon", one new operation_id per upload and image (base64 PNG, JPEG, WebP or GIF bytes, without a data URL prefix).

Use kind: "cover" for a cover. The input must be at most 10 MiB (14 MiB for the whole JSON request). The service checks ownership before decoding pixels, strips metadata, flattens animation, limits dimensions to 2048 pixels and stores a WebP up to 2 MiB. It rechecks consent, scope and board ownership before committing. Success returns { ok, board_id, asset_id }; fetch the bytes through boards.asset. Keep the same operation ID and exact source bytes on retries. Incomplete uploads never appear as board artwork.

Upload errors use the usual { code, message, hint } body:

  • 401 PT401 API_TOKEN_REQUIRED: the bearer token is missing or invalid.
  • 400 PT400 MISSING_FIELD: board_id, kind, operation_id or image is missing.
  • 400 PT400 UNKNOWN_FIELD: the body has any other field.
  • 400 PT400 INVALID_FIELD: the JSON, the base64 or the image is invalid.
  • 413 PT413 MEDIA_TOO_LARGE: the image or the request is too large.
  • 503 PT503 MEDIA_BUSY: the processor is busy. Retry later.
  • 403 PT403 BOARD_ACCESS_DENIED: ownership or permission was lost after the upload was prepared.
  • 503 PT503 MEDIA_UNCONFIRMED: the commit could not be confirmed. Retry with the same operation ID and bytes.

The usual API errors also apply, such as SCOPE_REQUIRED, API_RATE_LIMITED and ACCOUNT_BANNED.

boards.prepare_branding is the processor's scoped preparation endpoint: it accepts board_id, kind, operation_id and a lowercase SHA-256 source_hash, and returns { ticket }. A ticket cannot be committed by a connected app or reused across apps. Use boards.artwork_upload for a complete upload.

Stationery starts with plain paper. Catalogue entries include versioned artwork, access rules, token price, available and owned. Active supporters can use all active stationery and can still buy permanent ownership through boards.buy_stationery. A purchase requires boards:purchase and never charges twice on a retry. Owned items remain owned after rule changes or supporter expiry; published notes keep their original stationery snapshot. Reading token balances separately requires tokens:read.

Board errors and rate limits

Boards requests use the normal app/user API budget, plus shared per-account burst limits: 30 submissions/edits, 120 reaction changes and 10 invitations/reports per minute by default. Staff can change these limits. PT429 BOARD_RATE_LIMIT carries Retry-After. PT403 BOARDS_DISABLED means the emergency switch is off; stored data remains and boards.settings is still available. Do not discard drafts.

Other hints include BOARD_ACCESS_DENIED, BOARD_DRAFT_BASE_EXPIRED, BOARD_INVITATIONS_BLOCKED, INVALID_CURSOR, UNKNOWN_FIELD, MISSING_FIELD, INVALID_FIELD, ALREADY_EXISTS and DUPLICATE_OPERATION_ID. Display the supplied reason for a word-filter or moderation rejection. Artwork upload errors are listed under Board artwork and stationery.

  • Gateway rate limit: a 429 whose body has no code field (it looks like { "message": "API rate limit exceeded" }). This is the per-IP backstop of 1,000,000 requests a minute in front of the API, so you should not meet it; back off exactly as for PT429.
  • Token endpoint: OAuth errors use the standard shape { "error": "invalid_grant", "error_description": "…" }.
  • Blocked endpoints: an app token used on anything outside /v1/…, the OAuth token and userinfo endpoints, Storage and Realtime gets 403 with { "error": "oauth_client_forbidden", "error_description": "…" }.
  • Media: Storage answers with its own error objects (for example { "statusCode": "404", "error": "not_found", "message": "Object not found" }). A file the user may not see is a 404 or 400, never a 403.

Rate limits

Kotlin & JavaScript examples →

  • 120 requests per minute per app and user by default. This is the limit you will normally meet. It is a fixed window that resets at the start of each clock minute, keyed on your client id plus the user id.
  • A per-app ceiling of 600 requests per minute across all users and a burst cap of 100 requests per second per app by default. The burst cap answers PT429 with Retry-After: 1.
  • Need more? Open the app in the portal and use Request higher limits under Limits: say what the app does, how many users you expect and which limit you are hitting. Requests are reviewed by hand; an approval applies to the app immediately and the decision, with any note, shows on the same page. session.get always reports the limits that apply to your app.
  • Failed requests count. A PT400, a PT403, a PT401 CONSENT_REVOKED and even a call for a suspended app all consume budget, and denied calls are reported as "denied" in the portal's usage table. A retry loop against a broken token will rate-limit itself. Calls refused with API_TOKEN_REQUIRED or ACCOUNT_BANNED are stopped before the limit and don't count.
  • A PT429 response carries a Retry-After header in seconds. Every call that gets past the token check also returns RateLimit-Remaining and RateLimit-Reset (seconds until the minute resets) for the tighter of the two per-minute limits above. session.get returns rate_limit.remaining and rate_limit.reset_at for the current user so you can pace yourself before hitting the limit.
  • The gateway's per-IP backstop is 1,000,000 requests a minute with no hourly cap, so in practice the per-app and per-user limits above are the ones that apply. RateLimit-Remaining, RateLimit-Reset and Retry-After come only from PocketPass's own limits.

Media downloads and the token endpoint have their own limits (the token endpoint is 30 requests per minute per IP) and do not count against the API budget.

Keeping in sync

Kotlin & JavaScript examples →

Realtime pushes changes to you the moment they happen; use it whenever your app can hold a websocket open. Polling is the fallback for servers, for the seconds after a reconnect and for apps that cannot keep a socket. Two parameters make polling cheap:

  1. Poll conversations.list with updated_after set to the newest updated_at you have seen. The response contains only conversations that received a message since then, together with their last_message and unread_count. An empty items array is the common, cheap case.
  2. For the conversation that is open on screen, poll messages.list with changed_since set to the newest of created_at, edited_at and deleted_at you have seen. This returns new messages and messages that were edited or deleted after that instant, which updated_after on the conversation does not surface because edits and deletions do not bump a conversation's updated_at.
  3. With notifications:read, poll notifications.list with updated_after set to the newest updated_at you have seen.
  4. With encounters:read, poll encounters.list with updated_after set to the newest updated_at you have seen; a confirmation bumps it, so an encounter comes back once more when the other side confirms. tokens.get is one cheap call: re-fetch it on any tokens: event, or once a minute while a balance is on screen.

Recommended cadence: every 5 seconds while your app is in the foreground and a chat is visible, every 60 seconds in the background or when only the conversation list is showing. At 5 seconds a user with one open conversation uses 24 requests per minute — well inside the 120 per minute budget, with room for their own actions. Stop polling entirely when the window is hidden or the device is idle, and after a PT401, PT403 or PT429.

Keep the timestamps you pass back exactly as the API returned them (do not round to seconds). Because changed_since and updated_after are strict "after" comparisons, a message you already have will not be returned again, and a message with the same timestamp as your watermark is impossible in practice.

Catch-up pass. Items can change while you walk the pages of a list, and their timestamps come from when the change started. After a full walk, run the list again with updated_after set to the time the walk started minus one minute, and de-duplicate by id.

Unread state: call conversations.mark_read when the user actually sees the conversation, not on every poll — it is a write, it needs messages:write, and PocketPass uses it to clear the user's badge.

Presence

Always sort the two lowercase UUID user IDs. Do not always put the signed-in user first as friend-presence:me:friend: that only works when their ID sorts first. The reverse order is rejected as unauthorized. Use user IDs, not usernames or friend codes.

With presence:read, full profile objects include last_seen_at for yourself and, with friends:read, accepted friends with no block in either direction. Read it through friends.list, or me.get/profiles.get/profiles.get_many with their usual scopes. The key is omitted without permission, and is null if no activity has been recorded. It is an ISO 8601 timestamp of last recorded PocketPass app activity, not an exact disconnect time; a connected app tracking Presence does not update this timestamp. Use Realtime Presence for live online status. Refetch when needed; there is no last-seen broadcast event.

Presence is the ephemeral "who is here" state of a channel. With presence:read your app sees it on two kinds of topic it can already read: friend-presence:<lower user id>:<higher user id>, one per accepted friendship with the two ids sorted as strings (needs friends:read), tells whether that friend is online; conversation:<conversation id> (needs messages:read) tells who has the conversation open and who is typing. With presence:write your app may also track Presence there, which makes the connected user appear online to their friends and shows them as typing in a chat — the consent screen says so in as many words.

  • PocketPass itself tracks { user_id } on friend pairs and { user_id, active_conversation_id, is_typing } in conversations, keyed by the user id. Track the same shape so PocketPass and other apps understand you, and untrack or leave the channel when the user goes away.
  • Presence payloads come from clients and are not verified by the server: read the key and user_id as a hint, not as proof.
  • Joining a pair topic is refused unless the two users are friends right now; joining a conversation is refused unless the user is an active member. Tracking without presence:write is refused while the join itself succeeds.
  • Permissions are checked when a channel is joined and whenever you push a refreshed access_token, so a channel that is already open keeps working until the token expires (at most one hour) even after the user disconnects your app.

Connecting

Connect to wss://api.pocketpass.xyz/realtime/v1/websocket?apikey=<publishable key>&vsn=1.0.0. The publishable key is public and the same for every app: see https://developer.pocketpass.xyz/config.js. The user's access token goes into every join message, never into the URL.

Without a library, speak the Phoenix channel protocol over the socket: join, heartbeat every 30 seconds, and hand over each refreshed token before the previous one expires.

The join is answered with a phx_reply whose payload.status is "ok" or "error". Events then arrive as broadcast frames. Row events carry the database change; the other payloads are described above.

  • private: true is mandatory. A public channel with the same name joins happily and never receives anything.
  • The join is refused (a phx_reply with "status": "error") when your app lacks the scope, the user is not in that conversation, the topic belongs to someone else, or the user disconnected your app. Treat it like PT403 / PT401 on the API: do not retry in a loop.
  • record and old_record are the raw table rows, not the API objects, and their columns are not part of the API contract. The robust pattern is to treat an event as a signal and re-fetch through the API: messages.list with changed_since, conversations.list with updated_after, notifications.list with updated_after, friends.list / friends.requests_list, tokens.get, encounters.list with updated_after.
  • Send a heartbeat every 30 seconds or the server drops the socket. Access tokens last one hour: push the refreshed token with the access_token message, otherwise the channel closes when the old one expires.
  • Realtime does not count against the request budget, but it is a shared resource. Subscribe to the conversation on screen plus the user's notifications: topic, not to every conversation in the list; leave channels you no longer show.
  • Presence needs presence:read, and presence:write to appear online. The app_updates topic stays first-party, and connected apps cannot send Broadcast messages of their own.
  • While disconnected, poll as described in Keeping in sync, and re-fetch once after every reconnect — nothing is replayed.

Media

Kotlin & JavaScript examples →

Avatars and image attachments are files in two private buckets, referenced by path: profile.avatar_path lives in avatars, message.attachment.path in message-media. The same token that calls the API can read them, subject to the same rules — an avatar is readable when the user could see that profile (profile:read), an attachment when the user is a member of its conversation (messages:read).

Direct download

GET https://api.pocketpass.xyz/storage/v1/object/authenticated/avatars/<avatar_path>, or message-media/<path>, with the bearer token.

Use this from a server or a native app. The response is the file itself with its Content-Type. Files you may not read come back as a 404 or a 400, never a 403.

Signed URLs for browsers

An <img> tag cannot send a bearer token, so ask for short-lived signed URLs instead. Batch up to a whole page of avatars in one call to POST /storage/v1/object/sign/avatars with { "expiresIn": 600, "paths": [...] }. Each result has path, signedURL and error.

Or sign one file with POST /storage/v1/object/sign/message-media/<attachment path> and { "expiresIn": 600 }.

signedURL is relative. Prefix it with https://api.pocketpass.xyz/storage/v1 before you use it. The full URL then works without any headers, in an <img> or anywhere else.

  • expiresIn is in seconds and is clamped to 15 minutes (900); ask for a larger value and you silently get 900. Keep it short — a minute or two for a screen you are rendering now is plenty — and re-sign when the user comes back.
  • Revocation caveat: a signed URL is a bearer credential for that one file. It keeps working until it expires even if the user disconnects your app, blocks the other person or the message is deleted in the meantime. That is the reason for the 15-minute cap; do not cache signed URLs beyond the screen that requested them and never store them.
  • Signing a file the user may not see returns an error for that path (batch) or a 400/404 (single). Treat it as "no image".

Sending images

Upload the file first, then send the message that references it. Both steps use the same token and need messages:write. Upload with POST /storage/v1/object/message-media/<user id>/<conversation id>/<file name> and the image's Content-Type, then call messages.send with a client_operation_id and attachment: { path, mime_type }.

  • The path is exactly <user id>/<conversation id>/<file name>: the connected user's id (user_id from session.get), a conversation they are an active member of, and a file name of 1…128 characters made of letters, digits, ., _ and - that starts with a letter or digit. Use a fresh UUID per message as the name, and keep the same path on retries.
  • An app can neither overwrite nor delete uploads. Uploading to the same name again gets a 409 from Storage (the HTTP status, or "statusCode": "409" in a 400 body): the file is already there. Continue to messages.send with the same client_operation_id.
  • image/jpeg, image/png, image/webp and image/gif up to 10 MiB. Storage refuses other types and larger files; messages.send refuses a mime_type outside that list with PT400 UNSUPPORTED_MEDIA.
  • The upload is refused (a 400 or 403 from Storage) for another user's folder, for a conversation the user is not in, without messages:write, and after the user disconnects your app. messages.send double-checks the path (PT400 INVALID_ATTACHMENT_PATH) and that the file exists (PT404 ATTACHMENT_NOT_FOUND).
  • Omit body for an image-only message; it is stored as "📷", which is what PocketPass itself sends. A caption of 1…4000 characters is kept as the body.
  • An uploaded file that never ends up in a message is simply unused; there is nothing to clean up.
  • Avatars cannot be changed by apps.

Changing scopes

Kotlin & JavaScript examples →

A user approved a specific list of permissions, so the rules are:

  • Adding a scope disconnects every connected user. The moment you save an app with a scope it did not have before, all live grants are revoked and all sessions for your app are deleted. Users stay disconnected until they go through the connect flow again and approve the new list. The portal warns you and tells you how many users are affected before it saves.
  • Removing a scope disconnects nobody. Calls that needed the removed scope start answering PT403 SCOPE_REQUIRED immediately; everything else keeps working.
  • Name, description, website, logo and redirect URIs can be changed freely.

From your code's point of view a scope expansion looks exactly like the user disconnecting you: API calls answer PT401 CONSENT_REVOKED, and refreshing answers 400 with "error": "invalid_grant". Handle both in one place — forget the stored tokens, mark the account as disconnected, and show a "Reconnect PocketPass" action that starts the flow again. Because the consent screen shows the new permissions, users see what changed. If your app has an audience, add the scope during a quiet hour and ship the client that needs it first, so the reconnect prompt makes sense when it appears.

Idempotency

Kotlin & JavaScript examples →

Every Boards mutation, artwork upload, blocks.set and privacy.set uses the field operation_id, with the same once-per-action retry rules below. Existing messaging/friendship endpoints retain client_operation_id.

Networks drop responses. To make retries safe, these endpoints require a client_operation_id: messages.send, conversations.open, conversations.create, conversations.add_members, conversations.remove_member, conversations.leave, conversations.rename, friends.request_send, friends.request_respond and friends.remove.

  • Generate a fresh UUID once per user action — when the user presses "Send", not when you build the HTTP request.
  • Keep it with the pending action and reuse the same id on every retry of that action, including after a restart if you queue outgoing messages.
  • A retry with the same id and the same content returns the same result: for conversations.open and conversations.create the same conversation; for the friend endpoints the same request or the same removed answer.
  • For messages.send a retry returns the message as it is now, also after it was edited or deleted, after the sender left or was removed from the chat, and after a block. Its id is derived from the operation id, so there is never a duplicate row.
  • The same id with different content is refused with PT409 DUPLICATE_OPERATION_ID. For messages.send that means the id was already used for a message with another conversation, reply target or content that has never been edited or deleted. That is a bug in the caller, not something to retry.

Retry on network failures and on PT500, PT429 (after Retry-After) and HTTP 502/503/504. Do not retry PT400, PT401, PT403, PT404 or PT409 — the answer will not change.

fun requestJson(url: String, body: String, contentType: String = "application/json"): JSONObject {
    val connection = URL(url).openConnection() as HttpURLConnection
    try {
        connection.requestMethod = "POST"
        connection.connectTimeout = 15000
        connection.readTimeout = 30000
        connection.instanceFollowRedirects = false
        connection.doOutput = true
